
 
 # Invoice Type Suggestion for AR invoice types  Business Rule — Suggest Correct Invoice Type for AR Invoices Infer Invoice Type Code from Transaction Attributes  Execution Context Validate and classify AR invoice records (outgoing / sales invoices) provided by the application.  At execution time, the agent only knows: - the input records - their rows - their column names - the values present in those rows  Non-Hallucination Rule - Do NOT invent, infer, assume, or fabricate missing values. - Do NOT assume the existence of a field if it is not present. - Do NOT assume country, invoice type, correction intent, refund intent, or prepayment intent unless supported by available data. - Use only fields actually present in the input. - If a required value for a critical classification step is missing, report the exact missing field(s). - If the available evidence is insufficient or contradictory, do NOT guess a final classification with certainty; instead mark the invoice as Review Needed and explain why. - If a local alias (for example VAT, KOR, ZAL) is not explicitly supported by the available data, do not force a local label. Suggest the generic standardized semantic type code instead.  Analysis Start Rule - Start analysis by grouping records using:   1. batch_id   2. invoice_id - Validate each unique batch_id + invoice_id combination as one invoice. - Within each invoice:   - treat each unique line_id as one invoice line   - treat repeated header values across rows as invoice-level fields   - validate consistency of repeated invoice-level values across rows  Validation Objective Determine whether the declared invoice type code (if present) matches the observed transaction behavior, and suggest the most appropriate invoice type code when it is missing, ambiguous, or inconsistent.  The agent must: - infer invoice type from explicit document attributes when available - use transaction signals such as correction indicators, payment timing, original invoice references, and amount direction/signs - distinguish standard invoices, credit notes, corrected invoices, and prepayment invoices - detect contradictions between declared type and observed invoice behavior - suggest the most appropriate invoice type code without guessing unsupported facts - mark the invoice as Review Needed when invoice type is missing, inconsistent, or cannot be reliably inferred  Invoice Grouping Logic - Group rows by batch_id + invoice_id. - If one row represents one line, repeated header fields may appear on every row. - Treat each distinct line_id as a unique line item. - If the same invoice-level field appears with conflicting values in different rows of the same invoice, mark Review Needed. - If invoice type indicators repeat across rows, validate that repeated occurrences are consistent.  General Invalid Conditions A field is invalid if: - it is SQL NULL - it is the literal string "NULL" (case-insensitive) - it is empty or whitespace only - it contains conflicting repeated values for the same invoice-level attribute inside the same invoice  If any critical field required for invoice type classification is invalid or contradictory, mark Review Needed.  Country Determination Determine country using this precedence: 1. country 2. seller_address_country 3. buyer_address_country  Normalize country values where possible: - Belgium = BE - France = FR - Poland = PL  If country cannot be determined: - mark Review Needed - report COUNTRY_NOT_DETERMINED - suggest populating country or seller/buyer country fields  Invoice Type Universe Classify the invoice using the following generic semantic invoice type codes when supported by evidence:  - 380 = Commercial invoice   Use for standard AR sales invoices with normal sale behavior and no supported evidence of credit, correction, or prepayment intent.  - 381 = Credit note   Use when the invoice clearly represents a refund, reversal, cancellation impact, or a negative corrective effect against a prior invoice.  - 384 = Corrected invoice   Use when the invoice is a correction or replacement/re-issue of an earlier invoice, but is not behaving as a credit/refund note.  - 386 = Prepayment invoice   Use when the invoice requests advance payment, deposit, or down payment before the final invoice.  If evidence is insufficient to classify reliably: - do not force a type - mark Review Needed - use issue type = INSUFFICIENT_CLASSIFICATION_EVIDENCE  Local / Country-Specific Interpretation Apply one common semantic classification logic across Belgium, France, and Poland.  Country-specific interpretation: - Belgium (BE):   incorrect invoice type classification is blocking for domestic structured invoice generation where applicable - France (FR):   incorrect invoice type classification is blocking for domestic B2B structured e-invoicing and also problematic for accurate reporting payloads in other scenarios - Poland (PL):   incorrect invoice type classification is blocking for structured submission/reporting; if local business wording suggests VAT / KOR / ZAL, use that only as supporting evidence, but suggest the normalized semantic type code (380 / 381 / 384 / 386)  Important standardization rule: - Always prefer the generic semantic type code for the final suggestion. - If a country-specific/local alias is strongly evidenced, include it only as an explanatory note, not as the primary classification unless explicitly required by the data model.  Applicable Fields Use these fields when present. Field names may vary; rely only on available column names and values.  Identity / header candidates: - invoice_type_code - invoice_type - document_type - document_subtype - document_purpose - invoice_category - billing_reason  Correction / related-document candidates: - correction_indicator - is_correction - corrective_reason - correction_reason - original_invoice_reference - original_invoice_number - related_invoice_id - related_document_reference - replaced_invoice_reference  Credit / reversal / refund candidates: - credit_note_indicator - is_credit_note - refund_indicator - reversal_indicator - cancellation_indicator - return_indicator  Prepayment / advance candidates: - prepayment_indicator - advance_payment_indicator - deposit_indicator - down_payment_indicator - prepaid_amount - advance_amount - payment_stage - settlement_reference  Amount / sign behavior candidates: - tax_exclusive_total - tax_total - tax_inclusive_total - gross_total - payable_amount - line_extension_amount - line_tax_amount  Date / payment timing candidates: - issue_date - due_date - delivery_date - service_date - payment_terms  Text / free-text evidence candidates: - notes - invoice_description - document_description - reason_text - internal_comments - line descriptions  Use only fields actually present. If equivalent fields exist under different names, use the provided column names and explain which values were used.  Core Classification Principles Use available data conservatively. Prefer explicit document purpose or official type indicators over indirect behavioral clues. Do not overwrite source values. Do not guess hidden legal/business meaning.  Signal Priority Use signals in this order of reliability:  1. Explicit declared type indicators Examples: - invoice_type_code - invoice_type - document_type - document_purpose - correction / credit / prepayment flags  2. Explicit documentary evidence Examples: - original invoice reference - replacement/correction reason - refund/reversal/cancellation wording - advance/deposit/prepayment wording  3. Financial behavior Examples: - negative totals or negative net/tax/payable effect - positive totals with prepayment request - positive re-issued invoice replacing an earlier invoice  4. Related settlement/payment behavior Examples: - invoice requests money before final supply - invoice settles prior advance - invoice refers to prior issued document  If stronger signals conflict with weaker signals, prioritize stronger signals and flag the contradiction.  Inference Rules  1. Suggest 380 — Commercial invoice Suggest 380 when the invoice behaves like a normal sale and there is no supported evidence of: - refund / reversal / cancellation - correction / replacement of a previous invoice - advance / deposit / prepayment request  Typical supporting signals: - positive invoice amounts - ordinary payment terms - no correction indicators - no original invoice reference tied to correction or reversal - no prepayment/advance wording  2. Suggest 381 — Credit note Suggest 381 when the invoice clearly behaves like a credit note, refund, reversal, or negative corrective effect.  Typical supporting signals: - explicit credit note / refund / reversal / cancellation wording - negative totals, negative payable, negative line amounts, or clear negative net effect - reference to reversing or refunding an earlier invoice - return/cancellation intent  Important rule: - Negative amounts alone are not enough if explicit evidence instead indicates a corrective replacement invoice. - Positive amounts may still be a credit note in some source systems if explicit credit-note intent is present. - Use combined evidence, not sign alone.  3. Suggest 384 — Corrected invoice Suggest 384 when the invoice is a corrected or replacement invoice for an earlier one, but is not primarily behaving as a refund/credit note.  Typical supporting signals: - explicit wording such as corrected invoice, correction, replacement, re-issued - original invoice reference or replaced invoice reference - correction reason such as data fix, address correction, quantity correction, price correction - positive invoice values that replace/update the original invoice rather than refund it  Important rule: - If the document reduces value as a refund/reversal, prefer 381. - If the document re-issues or replaces the original invoice rather than refunding it, prefer 384.  4. Suggest 386 — Prepayment invoice Suggest 386 when the invoice requests payment in advance of the final invoice or final supply.  Typical supporting signals: - advance payment / prepayment / deposit / down payment wording - prepayment indicator or deposit indicator - prepayment or advance amount fields - payment requested before final settlement - references indicating later final invoice or settlement  Important rule: - A final invoice that merely references a prior prepayment is not automatically itself a prepayment invoice. - If the invoice appears to be the final settlement after advance payment, do not classify as 386 unless the document itself is the advance/prepayment request.  Contradiction Rules Mark Review Needed when: - invoice_type_code is missing and evidence is insufficient for reliable classification - invoice_type_code is present but conflicts with stronger observed evidence - repeated invoice rows contain conflicting invoice type indicators - the invoice is marked as credit note but behavior strongly matches a normal invoice - the invoice is marked as prepayment but shows normal final-sale behavior with no advance-payment evidence - the invoice is marked as corrected invoice but no correction/replacement evidence exists - multiple invoice type signals are present and materially conflict  Examples of contradictions: - declared as credit note, but all amounts are positive and no refund/reversal/correction evidence exists - declared as prepayment invoice, but no advance/deposit/prepayment indicators exist and the invoice behaves as a final standard sale - declared as corrected invoice, but no original-invoice linkage or correction reason exists and behavior matches a standard invoice - declared as commercial invoice, but explicit refund/reversal indicators or correction indicators exist  Consistency Checks Across the Invoice Validate: - repeated invoice_type_code or invoice_type values across rows are consistent - repeated correction indicators, prepayment indicators, and related-document references do not conflict - text evidence and numeric behavior do not materially contradict the suggested type - if one row indicates credit note and another indicates commercial invoice for the same invoice ? mark Review Needed  Severity Rules  Critical failures ? Review Needed - invoice type code is missing and reliable classification cannot be made - invoice type code is present but clearly conflicts with stronger evidence - repeated rows contain conflicting invoice type indicators - country cannot be determined - correction / credit / prepayment classification is material for downstream structured reporting and the available evidence indicates a mismatch - insufficient evidence for reliable classification in a blocking scenario  Medium severity - weak or indirect evidence suggests a different invoice type but not conclusively - local alias and generic code appear inconsistent, but the semantic type is still reasonably inferable - invoice type appears inferable but one supporting reference is missing  Warnings - invoice type is likely correct but supporting metadata is sparse - local label could not be confirmed, but generic semantic classification is still clear  Final Decision Rules Mark invoice as Review Needed if any of the following occurs: - invoice type code is missing - invoice type code is present but does not match observed invoice behavior - conflicting invoice type evidence exists across rows - country cannot be determined - evidence is insufficient to classify reliably - the invoice type is not safe for downstream structured VAT e-invoice / e-reporting processing  Mark invoice as PASS only if: - invoice type is present or can be reliably inferred from available evidence - declared invoice type is consistent with observed transaction behavior - repeated invoice-level type indicators do not conflict - only non-blocking ambiguity remains  Structured Processing Readiness Rule This validation checks invoice type classification readiness only. It does NOT certify every other XML, tax, legal, semantic, or arithmetic requirement.  Use the following wording: - "Safe for downstream structured XML/reporting generation from an invoice-type-classification perspective only" when classification is consistent and supported - "NOT safe for downstream structured XML/reporting generation until invoice-type issues are resolved" when any blocking issue exists  Country-specific interpretation of readiness: - Belgium domestic B2B AR:   Review Needed = not safe for downstream structured invoice generation - France domestic B2B AR:   Review Needed = not safe for downstream structured invoice generation - France B2C / cross-border AR:   Review Needed = not safe for accurate reporting payload generation - Poland AR:   Review Needed = not safe for downstream structured submission/reporting  Only invoices passing all invoice-type checks are safe for downstream structured processing from the invoice-type-classification perspective. At execution time, the agent only knows: - the input records - their rows - their column names - the values present in those rows  Non-Hallucination Rule - Do NOT invent, infer, assume, or fabricate missing values. - Do NOT assume the existence of a field if it is not present. - Do NOT assume country, invoice type, tax treatment, adjustment logic, or business meaning unless supported by available data. - Only use fields actually present in the input. - If a required value for a specific validation step is missing, mark that step as not fully verifiable and report the exact missing field(s). - If a critical amount field required for core mathematical validation is missing, invalid, or conflicting, mark the invoice as Review Needed. - If the invoice appears to imply a financial scenario (for example credit note, corrective invoice, prepayment, reverse charge, exempt supply, or mixed VAT) but the required fields to validate that scenario are missing, do not guess the missing logic; instead report that the invoice cannot be fully validated from the provided data. Tolerance Rules Use tolerances to reduce false mismatches caused by expected financial rounding: - Amount tolerance = 0.02 - Tax rate tolerance = 0.01 percentage points unless the data format clearly stores rates differently - When comparing repeated totals across rows, use the same amount tolerance unless exact equality is required by context  Do not classify a discrepancy as harmless rounding if: - the mismatch clearly exceeds tolerance - the mismatch scales across multiple lines in a way suggesting missing or duplicate amounts - the mismatch affects more than one critical total in a consistent direction - the mismatch indicates stale or conflicting header totals  Country-Specific AR Context Rules Apply this prompt to AR invoices only. Core Calculation Principles Use available data conservatively. Prefer direct monetary amounts over reconstructed calculations when both are present. Do not overwrite source values. Do not invent absent adjustment logic.  1. Line Aggregation Compute from available line values: - SumNetLines = sum of line_extension_amount or equivalent line net amount - SumTaxLines = sum of line_tax_amount where present - SumGrossLines = sum of line_gross_amount where present - SumLineAllowances = sum of line_allowance_amount where present - SumLineCharges = sum of line_charge_amount where present - SumLineRounding = sum of line_rounding_amount where present  If multiple candidate line net fields exist, prefer the one most clearly representing line net/tax-exclusive amount. If a line amount field is missing for some lines, do not guess it from unrelated values unless quantity and unit_price allow a line-level arithmetic check.  2. Invoice-Level Base Logic When available and applicable, apply: - ComputedLineExtensionTotal = SumNetLines - ComputedTaxExclusive = SumNetLines - allowance_total + charge_total + rounding_amount - ComputedTaxTotal = SumTaxLines - ComputedTaxInclusive = ComputedTaxExclusive + ComputedTaxTotal - ComputedPayable = ComputedTaxInclusive - prepaid_amount + payable_rounding_amount  If allowance_total is absent, treat it as zero for this formula only. If charge_total is absent, treat it as zero for this formula only. If prepaid_amount is absent, treat it as zero for this formula only. If rounding_amount is absent, treat it as zero for this formula only. If payable_rounding_amount is absent, treat it as zero for this formula only.  Important interpretation note: - Treat zero-by-default only as a calculation fallback for absent optional adjustment fields. - Do NOT assume the invoice has no adjustment business logic elsewhere if the data suggests otherwise. - If the invoice clearly implies adjustments but the necessary fields are not present, report incomplete verifiability and consider Review Needed if payable or gross totals cannot be reconciled.  3.
